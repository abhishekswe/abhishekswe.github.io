Node's built-in WebSocket drops CDP replies over 4 MB

Chromium's DevTools endpoint compresses its WebSocket frames, and Node's built-in client refuses any compressed message that inflates past 4 MB. The connection closes with 1006 and the reply is gone. Here is the repro, and the fix: --remote-debugging-pipe.

What I saw

I was writing a small Node tool that drives Brave over the Chrome DevTools Protocol (CDP). To keep it dependency-free I used the WebSocket that ships with Node. Small commands worked. DOMSnapshot.captureSnapshot on real pages did not: the socket closed with code 1006, no reason, and the pending command never got a reply.

1006 means "closed abnormally", which usually points at a crashed browser or a network problem. Neither was happening. The browser was fine, and the next connection worked.

Why it happens

Two defaults meet:

  1. Node's client offers the permessage-deflate extension and Chromium's DevTools server accepts it, so large CDP replies arrive compressed. They are JSON, so they compress very well.
  2. Node's WebSocket is implemented by undici, which limits how large a single compressed message may get once inflated: kDefaultMaxDecompressedSize = 4 * 1024 * 1024. It is a guard against compression bombs. Past the limit undici raises MessageSizeExceededError internally and fails the connection.

Your code never sees that error. It sees a close event with code 1006.

Repro

Start a headless browser with a debugging port (any Chromium works; I used Brave):

"/Applications/Brave Browser.app/Contents/MacOS/Brave Browser" \
  --headless=new --remote-debugging-port=9339 \
  --user-data-dir=/tmp/cdp-test about:blank

Then ask a page for strings of different sizes:

// probe.mjs (Node 22+, no dependencies)
const list = await (await fetch('http://127.0.0.1:9339/json/list')).json();
const url = list.find((t) => t.type === 'page').webSocketDebuggerUrl;

function tryMB(mb) {
  return new Promise((resolve) => {
    const ws = new WebSocket(url);
    ws.addEventListener('open', () => {
      ws.send(JSON.stringify({
        id: 1,
        method: 'Runtime.evaluate',
        params: { expression: `'x'.repeat(${mb} * 1024 * 1024)`, returnByValue: true },
      }));
    });
    ws.addEventListener('message', () => {
      console.log(mb, 'MB: reply received');
      ws.close();
    });
    ws.addEventListener('close', (e) => {
      console.log(mb, 'MB: close', e.code);
      resolve();
    });
  });
}

for (const mb of [3, 3.9, 4.1, 5]) await tryMB(mb);

On Node 24.15 (undici 7.24.4) against Chromium 156:

Reply sizeResult
3 MBreply received, close 1000
3.9 MBreply received, close 1000
4.1 MBno reply, close 1006
5 MBno reply, close 1006

Logging ws.extensions after open prints permessage-deflate; client_max_window_bits=15, so you can confirm compression is on.

Where CDP replies get that big

  • DOMSnapshot.captureSnapshot: a page with about 30,000 elements gave me an 11 MB snapshot.
  • Full-page Page.captureScreenshot, which comes back as base64.
  • Network.getResponseBody for large scripts or JSON responses.
  • Runtime.evaluate with returnByValue on large objects.

The fix: talk to the browser over a pipe

Chromium can take CDP over a pair of file descriptors instead of a port. Start it with --remote-debugging-pipe and it reads commands on fd 3 and writes replies on fd 4, each message being JSON followed by a NUL byte. There is no compression, no message size limit, and no debugging port open for other processes on the machine to reach.

import { spawn } from 'node:child_process';

const browser = spawn(BROWSER_PATH, [
  '--headless=new', '--remote-debugging-pipe', `--user-data-dir=${profileDir}`,
], { stdio: ['ignore', 'ignore', 'ignore', 'pipe', 'pipe'] }); // fd 3 in, fd 4 out

const toBrowser = browser.stdio[3];
const fromBrowser = browser.stdio[4];

let chunks = [];
fromBrowser.on('data', (data) => {
  let start = 0;
  for (let end = data.indexOf(0); end !== -1; end = data.indexOf(0, start)) {
    chunks.push(data.subarray(start, end));
    onMessage(JSON.parse(Buffer.concat(chunks).toString('utf8')));
    chunks = [];
    start = end + 1;
  }
  if (start < data.length) chunks.push(data.subarray(start));
});

const send = (message) => toBrowser.write(JSON.stringify(message) + '\0');

Two things to get right:

  • A large reply arrives as many data chunks. Buffer until the NUL byte; don't parse each chunk.
  • The pipe connects you to the browser, not to a page. Open one with Target.createTarget, attach with Target.attachToTarget and flatten: true, then send page commands with the returned sessionId.

The same test over the pipe: 5 MB and 11 MB replies both arrived in full.

If you need a WebSocket

The pipe only works for a browser you launch. To attach to one that is already running you need the port. In that case use a client that lets you set the limit yourself, such as the ws package and its maxPayload option, and keep large replies in mind.

If a Node CDP client closes with 1006 only on big pages, check the reply size before blaming the browser. Node's built-in WebSocket stops at 4 MB inflated.
