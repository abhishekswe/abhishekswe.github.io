A regex fast path let an auth bypass through my LLM ship gate

agent-fastpath decides obvious ship-gate cases with plain rules before it calls a model. One of those rules approved a diff that removed an auth check, because the same input also said Tests: 214 passed, 0 failed. The model never saw it.

The setup

agent-fastpath is an MCP server that coding agents (Claude Code, Codex, Cursor) call before they act. Its ship gate takes CI output and answers accept, review or escalate. Most answers come from a model, TypeSafe's Jev. Calling a model for Tests: 64 passed, 0 failed is a waste, so a deterministic engine decides the obvious cases first.

The first version of that engine was two checks:

const failure = SHIP_GATE_FAILURE_PATTERNS.find((p) => p.test(rawText));
if (failure) return { decision: 'BLOCKED', confidence: 1.0 /* ... */ };

const pass = SHIP_GATE_PASS_PATTERNS.find((p) => p.test(rawText));
if (pass) return { decision: 'READY_TO_SHIP', confidence: 0.99 /* ... */ };

// anything else goes to the model

The bad approval

Agents don't send clean CI logs. They send what they have, which is often a diff with the test summary at the end:

diff --git a/src/auth.ts b/src/auth.ts
--- a/src/auth.ts
+++ b/src/auth.ts
@@ -10,2 +10,2 @@
-  if (!session) throw new UnauthorizedError();
+  // bypassed auth
Tests: 214 passed, 0 failed

No failure pattern matched. A pass pattern did. The engine returned READY_TO_SHIP at 0.99 and the model never read the diff.

Passing tests tell you the code does what the tests check. They say nothing about a deleted auth check that no test covers, and that is exactly the kind of change the model was there to catch.

The bad blocks

The failure side was too loose in the other direction. This pattern:

/\b[1-9]\d*\s+(?:failed|failing|errors?)\b/i

blocked ordinary sentences that happen to contain a number and the word "failed" or "error":

  • Locks account after 2 failed login attempts
  • Retries up to 3 errors before timing out
  • Handles HTTP 500 errors gracefully
  • Returns 401 error when auth header is missing

A TDD write-up like Red phase: Tests: 1 failed. Green phase after fix: Tests: 5 passed, 0 failed was blocked too, for a failure that had already been fixed.

A false block is annoying but safe: the agent stops and asks. The false approval was the real bug.

The fix

const hasDiff = /\b(?:diff --git|@@ -\d+,\d+ \+\d+,\d+ @@|\bindex [0-9a-f]{7,}\.\.[0-9a-f]{7,})\b/.test(rawText);
const failure = SHIP_GATE_FAILURE_PATTERNS.find((p) => p.test(rawText));
const pass = SHIP_GATE_PASS_PATTERNS.find((p) => p.test(rawText));

if (failure) {
  const isTestCountFailure = /\b(?:test result:\s*FAILED|Tests:\s+[1-9]\d*\s+failed|[1-9]\d*\s+failed,\s*\d+\s+passed|[1-9]\d*\s+failing)\b/i.test(rawText);
  const hasExplicitZeroFailed = /\b(?:0 failed|failed:\s*0)\b/i.test(rawText);
  if (!(isTestCountFailure && hasExplicitZeroFailed)) return BLOCKED;
}

if (pass && !failure && !hasDiff) return READY_TO_SHIP;

// anything else goes to the model
  • A diff disables the green fast path. If the input carries code, the model reads it.
  • Failure patterns look like test-runner output (Tests: 3 failed, test result: FAILED, 2 failed, 10 passed, 4 failing), not any number followed by "failed".
  • Mixed signals go to the model. A "1 failed" next to a "0 failed" is a story about a fix, not a verdict.

Running the old and the new engine on the inputs above:

InputBeforeAfter
Auth-bypass diff + "214 passed, 0 failed"READY_TO_SHIPsent to model
The four ordinary sentencesBLOCKEDsent to model
Red/green TDD summaryBLOCKEDsent to model
Tests: 64 passed, 0 failedREADY_TO_SHIPREADY_TO_SHIP

Each case is now a regression test. The change is in this commit.

The rule I use now

A fast path is a cheap way to say no. It may say yes only when the input contains nothing it doesn't understand. If a diff, a config change or free text rides along, the fast path steps aside and the reviewer reads it.

Blocking early on a clear failure errs toward a person taking a look. Approving early skips the only part of the system that reads meaning. So when I add a rule, I first ask which way it moves the verdict. Rules that tighten can be broad. Rules that loosen need proof that the input is only what they were written for.
